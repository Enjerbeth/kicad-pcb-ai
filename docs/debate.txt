ROADMAP Y ARQUITECTURA: Agente LLM para Hardware-as-Code (HaC)

1. Deconstrucción del Ecosistema

El objetivo de este proyecto es construir un puente determinista entre el razonamiento espacial/lógico de un Modelo de Lenguaje Grande (LLM) y un motor de diseño de circuitos impresos (EDA). El sistema automatiza el diseño electrónico separando la intención de diseño (generada por la IA) de la ejecución física (compilada por scripts).



Entorno de Ejecución:



IDE Principal: Google Antigraviti (Alojamiento del Agente IA y ejecución del Middleware).

Motor EDA de Destino: KiCad 8.

Motor Lógico: SKiDL (Generación procedimental de Netlists).

Motor Físico: API nativa en Python de pcbnew (Manipulación geométrica y enrutamiento en KiCad).

2. Diagnóstico de la Arquitectura de Datos (El Pipeline)

El flujo de datos es unidireccional y se divide en tres dominios estrictamente aislados. Se requiere que las IAs consultadas evalúen este flujo y sugieran optimizaciones de seguridad o validación.



Dominio 1: Intención (Capa IA). El Agente recibe el requerimiento humano (ej. "Diseña un divisor de tensión aislado") y emite una respuesta estrictamente estructurada en un formato de datos (JSON), sin generar código ejecutable.

Dominio 2: Middleware (Capa Intérprete). Un script desarrollado en Python que vive en el IDE. Su función es ingerir el JSON, validar la integridad de los datos, y traducir las instrucciones a funciones de SKiDL.

Dominio 3: Síntesis (Capa EDA). El Middleware genera dos artefactos: un archivo .net (Netlist) y un script macro en Python. El Netlist se importa en KiCad, y el script macro se ejecuta dentro de la consola embebida de KiCad para organizar espacialmente las huellas (Footprints).

3. Desarrollo de Fases (Roadmap de Implementación)

Se solicita a las IAs que revisen las siguientes cuatro fases y aporten estrategias de optimización, algoritmos matemáticos para posicionamiento, o métodos de validación de esquemáticos.



Fase 1: Estandarización del Prompt System (Ingeniería del Agente)

El Agente debe ser configurado con reglas inquebrantables para evitar alucinaciones en librerías de KiCad.



Regla de Salida: Obligación de responder únicamente con una estructura JSON validable contra un JSON Schema predefinido.

Diccionario de Componentes: El Agente debe tener en su contexto base un diccionario inmutable con los nombres exactos de las librerías oficiales de KiCad (ej. Device:R, Sensor_Temperature:NTC).

Estructura de Datos Obligatoria: El JSON debe contener arreglos independientes para Metadatos del Proyecto, Nodos de Componentes (con designadores, valores y huellas exactas), Matriz de Conexiones (Netlists mapeados pin a pin) y Coordenadas de Layout (X, Y en milímetros, más rotación en grados).

Fase 2: Construcción del Middleware de Validación (Python)

Desarrollo del motor que traduce el JSON a instrucciones EDA. Aspectos a evaluar por las IAs:



Módulo de Ingesta: Lógica para parsear el JSON y manejar excepciones (ej. qué hacer si el Agente inventa un pin que no existe en el componente).

Módulo Lógico (SKiDL): Instanciación dinámica de objetos Part y Net. Implementación del chequeo de reglas eléctricas (ERC) automatizado.

Módulo de Generación: Escritura del archivo .net en disco.

Fase 3: Algoritmos de Posicionamiento Físico (pcbnew)

El Middleware debe autogenerar la macro para KiCad. Se requiere aporte algorítmico en:



Traducción Geométrica: Mapeo de coordenadas relativas (del JSON) a coordenadas absolutas en milímetros (usando VECTOR2I y EDA_ANGLE).

Prevención de Colisiones: Implementación de un algoritmo de Bounding Box en el Middleware para garantizar que el Agente no posicione dos huellas en las mismas coordenadas espaciales.

Enrutamiento Inicial (Pistas): Evaluación sobre si el agente debe definir pistas (Tracks) simples mediante arreglos de nodos (X, Y), o si es mejor delegar esta tarea a un enrutador automático externo (ej. Freerouting).

Fase 4: Bucle de Retroalimentación (Feedback Loop Automático)

Fase avanzada para automatización total. Solicitud de diseño arquitectónico a las IAs:



Captura de Errores ERC/DRC: Si SKiDL falla al compilar el circuito (por ejemplo, salida conectada a salida), el Middleware no debe detenerse de forma fatal.

Auto-Corrección: El Middleware debe capturar el volcado de error (Stack Trace), inyectarlo nuevamente en el contexto del Agente en el IDE mediante la API, y solicitar una versión corregida del JSON.



4. Entregables Esperados de las IAs Consultadas

### 1. Vulnerabilidades Críticas en el Flujo (JSON -> SKiDL -> pcbnew)



**A. Alucinación de Pines y Mapeo Inverso (Falla Crítica en SKiDL)**

* **Problema:** Los LLMs suelen desconocer el número exacto de pines o su nomenclatura en huellas específicas. Si el LLM especifica una conexión al pin `VCC`, pero la librería de KiCad lo nombra `VDD` o `Pin_1`, SKiDL lanzará una excepción fatal.

* **Mitigación:** El Middleware debe implementar un *Shadow Interrogator*. Antes de pasar el JSON a SKiDL, el Middleware debe instanciar silenciosamente los componentes en memoria para extraer su lista de pines válidos. Si el JSON del LLM hace referencia a un pin inexistente, el Middleware debe usar un algoritmo de *Fuzzy String Matching* (ej. distancia de Levenshtein) para sugerir el pin correcto, o fallar gracefully antes de la compilación.



**B. El Abismo del Razonamiento Espacial del LLM (Falla en pcbnew)**

* **Problema:** Los LLMs no tienen un motor espacial interno confiable. Pedirle coordenadas `(X, Y)` absolutas resultará en huellas superpuestas, orientaciones ilógicas y PCBs inenrutables. El Bounding Box propuesto en la Fase 3 evitará colisiones, pero no garantizará enrutabilidad.

* **Mitigación:** Eliminar la responsabilidad de las coordenadas absolutas del LLM. El JSON del LLM debe contener **Topología y Restricciones**, no geometría. (Ver sección 3 para algoritmos).



**C. Desincronización de Designadores (Netlist vs. Layout)**

* **Problema:** Si el LLM genera designadores (`U1`, `R1`, `C2`), y SKiDL los reasigna o los reordena durante la compilación, el script de `pcbnew` (que usa los designadores del LLM) colocará componentes equivocados.

* **Mitigación:** SKiDL debe ser forzado a respetar los designadores del JSON. Alternativamente, el Middleware debe generar un diccionario de mapeo `{designador_llm: designador_skidl}` que el script de `pcbnew` utilice como traductor.



**D. Bucle Infinito en el Feedback Loop (Fase 4)**

* **Problema:** Si el LLM no logra entender el error ERC inyectado, entrará en un bucle infinito de correcciones fallidas, consumiendo tokens y tiempo.

* **Mitigación:** Implementar un contador de intentos (`max_retries = 3`). Si se supera, el Middleware debe detenerse, guardar el log de errores y notificar al usuario humano para intervención manual.

### 2. Optimización Estructural: JSON Schema Ideal



Para evitar ambigüedad, el JSON no debe ser una lista plana de conexiones, sino un grafo dirigido con restricciones. La estructura debe separar explícitamente la definición del componente de su topología.



**Estructura JSON Sugerida:**



```json

{

"project_metadata": {

"name": "Divisor de Tensión Aislado",

"pcb_constraints": {

"board_shape": "rectangular",

"dimensions_mm": [50, 50],

"layer_count": 2

}

},

"components": [

{

"id": "R1",

"library": "Device:R",

"footprint": "Resistor_SMD:R_0805_2012Metric",

"value": "10k",

"layout_role": "divider_top"

}

],

"nets": [

{

"name": "VCC_DIV",

"type": "power",

"connections": [

{"component_id": "R1", "pin": "1"},

{"component_id": "R2", "pin": "2"}

]

}

],

"layout_hints": {

"clusters": [

{"name": "divisor_network", "components": ["R1", "R2"], "pattern": "vertical_stack"}

],

"rules": [

{"type": "keepout", "target": "U1", "distance_mm": 5.0}

]

}

}

```



**Mejoras clave en este Schema:**

1. **`layout_hints` en lugar de coordenadas:** El LLM define relaciones (clusters, patrones) en lugar de coordenadas absolutas `(X,Y)`. El Middleware traduce `vertical_stack` a geometría.

2. **`pin` explícito:** Se exige el número de pin lógico o el nombre exacto, facilitando la validación previa en SKiDL.

3. **`type` en nets:** Ayuda a SKiDL a aplicar reglas ERC específicas (ej. una red tipo `power` no puede conectarse a un pin `passive` sin un símbolo de power flag).

### 3. Algoritmos para Posicionamiento Físico Paramétrico (pcbnew)



Ya que retiramos la carga geométrica al LLM, el Middleware debe contener un motor de "Layout Interpretativo". Aquí se presentan estrategias algorítmicas para la Fase 3.



#### A. Algoritmo de Layout Basado en Grafos (Force-Directed Graph Layout)

Para componentes discretos sin un patrón geométrico obvio, las coordenadas pueden calcularse tratando los componentes como nodos y los nets (conexiones) como resortes.



**Lógica del Algoritmo:**

1. **Construcción del Grafo:** Crear un grafo `G(V, E)` donde `V` son los componentes y `E` son las redes que los conectan.

2. **Pesos de Resortes:** Asignar un peso a cada arista basado en la criticidad de la señal (ej. señales de alta frecuencia = resorte más rígido/distancia más corta).

3. **Iteración Física:** Aplicar el algoritmo de Fruchterman-Reingold. Los componentes se atraen si están conectados eléctricamente y se repelen levemente si no lo están (prevención de colisiones).

4. **Exportación:** Las coordenadas resultantes `(X, Y)` en el espacio continuo se escalan a la grilla de `pcbnew` (ej. 1.27mm) y se inyectan en la macro de Python.



#### B. Algoritmos de Patrones Paramétricos Específicos

El Middleware debe tener una librería de funciones geométricas que se activan cuando el LLM emite un `layout_hint`.



**1. Distribución Radial (Ej. Anillo de LEDs):**

```python

def calcular_layout_radial(componentes_ids, centro=(25,25), radio=10):

n = len(componentes_ids)

posiciones = {}

for i, comp_id in enumerate(componentes_ids):

angulo = (2 * math.pi / n) * i

x = centro[0] + radio * math.cos(angulo)

y = centro[1] + radio * math.sin(angulo)

rotacion = math.degrees(angulo) + 90 # Orientar hacia el centro

posiciones[comp_id] = (x, y, rotacion)

return posiciones

```



**2. Mallas Matriciales (Bancos de Resistencias/Capacitores):**

```python

def calcular_layout_matriz(componentes_ids, origen=(10,10), pitch_x=2.54, pitch_y=2.54, columnas=4):

posiciones = {}

for i, comp_id in enumerate(componentes_ids):

fila = i // columnas

col = i % columnas

x = origen[0] + (col * pitch_x)

y = origen[1] + (fila * pitch_y)

posiciones[comp_id] = (x, y, 0) # Rotación 0 estándar

return posiciones

```



#### C. Enrutamiento Inicial (Pistas)

**Evaluación y Recomendación:** El LLM **jamás** debe definir las pistas (tracks). Definir pistas requiere conocer el *Design Rule Check (DRC)* (grosor mínimo, separación, capas). Un track generado por el LLM violará reglas de fabricación.



**Solución Óptima:**

1. La macro de `pcbnew` solo debe posicionar huellas (Footprints) usando `VECTOR2I` y `EDA_ANGLE`.

2. Una vez posicionadas, el Middleware debe generar todas las conexiones lógicas en `pcbnew`.

3. **Delegar el enrutamiento:** El Middleware debe exportar el archivo `.kicad_pcb` semiacabado e invocar mediante subprocess a **Freerouting** (o al enrutador interno de KiCad 8 mediante su API de scripting) con un archivo de reglas DRC preconfigurado.

4. Una vez que Freerouting termina, el Middleware importa el archivo enrutado de vuelta al proyecto KiCad.

### 4. Arquitectura del Bucle de Retroalimentación (Fase 4)



Para que la Fase 4 funcione sin volverse inmanejable, el Middleware no debe inyectar un "Stack Trace" crudo de Python. Los LLMs se confunden con errores de bajo nivel de Python.



**Diseño del Inyector de Errores:**

El Middleware debe interceptar el error de SKiDL o el DRC de KiCad y traducirlo a un "Error Humano-Lógico".



* *Error crudo de Python:* `ValueError: Cannot connect Part U1 pin 1 to Part U2 pin 3 because they are both outputs.`

* *Payload inyectado al LLM (Vía API):*

```json

{

"feedback_status": "ERC_FAILED",

"error_type": "pin_conflict",

"description": "Pin 1 of U1 (Output) is connected to Pin 3 of U2 (Output). This creates a short circuit.",

"instruction": "Please review the JSON 'nets' array for the connection between U1 and U2. Either change the pin mapping, add a series resistor, or correct the component types."

}

```



Al inyectar este JSON estructurado de error en el contexto del LLM junto con el prompt original, el agente tiene una altísima probabilidad de devolver un JSON corregido en el siguiente ciclo, logrando la automatización total de la Fase 4.

1. Vulnerabilidades: puntos de fallo críticos en el pipeline JSON → SKiDL → pcbnew



a) Desfase entre el diccionario de componentes y las librerías reales de KiCad



· Riesgo: el diccionario “inmutable” podría quedar obsoleto si la versión de KiCad instalada en el entorno de ejecución no coincide exactamente con los nombres de huellas y librerías que maneja el LLM. Un simple cambio de sufijo (Resistor_SMD:R_0805_2012Metric vs Resistor_SMD:R_0805_2012Metric_Pad1.20x1.40mm_HandSolder) rompe la generación de la netlist.

· Consecuencia: SKiDL no encontrará la huella y fallará en la instanciación. Si la validación no es exhaustiva, se generará un archivo .net inconsistente que KiCad rechazará al importarlo.



b) Mapeo de pines ambiguo y dependencia de la nomenclatura lógica vs. física



· Riesgo: el JSON usa los nombres lógicos de los pines (p. ej. “VCC”, “GND”, “IN+”) que el LLM inventa o extrae de un contexto incompleto. Muchos componentes en SKiDL definen sus pines con números (“1”, “2”) y solo algunos aceptan alias.

· Consecuencia: durante la conexión de redes, el middleware (SKiDL) lanzará una excepción PinNotFound. Si el bucle de feedback no formatea el error en términos del esquema JSON original, el agente no entenderá cómo corregir (por ejemplo, el stack trace contiene detalles internos de SKiDL que el LLM no sabe interpretar).



c) Validación de reglas eléctricas (ERC) fuera del contexto nativo de KiCad



· Riesgo: el plan menciona “chequeo de reglas eléctricas (ERC) automatizado” en el módulo lógico. SKiDL por sí solo no realiza ERC; solo construye el circuito. Para detectar conflictos (salidas conectadas a salidas, ausencia de alimentación, etc.) haría falta invocar el ERC de KiCad desde la API de pcbnew, lo cual requiere que el esquemático ya esté generado y cargado en memoria.

· Consecuencia: los errores eléctricos solo se detectan tardíamente, durante la importación en KiCad o al lanzar el ERC manualmente. Esto retrasa la fase de auto-corrección y puede generar bucles iterativos largos si el feedback es débil.



d) Colisiones y coordenadas absolutas sin retroalimentación geométrica real



· Riesgo: el Middleware ejecuta el posicionamiento usando coordenadas del JSON. Si se implementa un algoritmo de Bounding Box, éste debe cargar primero la geometría real de la huella desde la librería de KiCad. Cargar huellas una por una en el entorno de pcbnew puede ser costoso y propenso a errores si la librería no está accesible desde el entorno de ejecución del Middleware (que se ejecuta fuera de KiCad). El plan sugiere que el script de layout se ejecuta dentro de la consola de KiCad, pero la prevención de colisiones se especifica para el Middleware (fuera de KiCad). Hay un conflicto de contexto.

· Consecuencia: si la detección de colisiones se intenta sin datos reales, se corre el riesgo de colocar componentes con solapamiento real no detectado, lo que genera DRCs (Design Rule Check) al final y obliga a rehacer el layout.



e) Bucle de auto-corrección con contexto limitado



· Riesgo: la inyección del stack trace en el contexto del agente puede superar la ventana de tokens o contener información no filtrada (rutas de archivos locales, nombres de variables internas) que confunden al LLM y lo llevan a generar JSONs aún más incorrectos.

· Consecuencia: la retroalimentación se vuelve contraproducente; el agente puede alucinar soluciones inválidas repetidamente si no se le provee un formato estructurado con la causa raíz y la sugerencia de corrección.

2. Optimización Estructural: esquema JSON ideal para eliminar ambigüedades



El objetivo es que el JSON no requiera interpretación subjetiva por parte del Middleware y que cada campo esté directamente vinculado a una primitiva de SKiDL o pcbnew. Propongo un esquema modular con las siguientes características:



```json

{

"project": {

"name": "voltage_divider",

"version": "1.0",

"units": "mm",

"grid_origin": {"x": 100.0, "y": 100.0}

},

"parts": [

"part_def": "Device:R", // SKiDL part library:name

"placement": {

"strategy": "absolute",

"x": 110.0, "y": 100.0,

"rotation": 0,

"side": "top"

}

},

{

"ref": "D1",

"pins": ["A", "K"],

"placement": {

"strategy": "grid",

"grid_params": {

"origin": {"x": 120.0, "y": 80.0},

"rows": 1, "cols": 4,

"spacing_x": 5.0, "spacing_y": 0.0

},

"rotation": 0,

"side": "top"

}

}

],

"nets": [

{

"name": "VOUT",

"connections": [

{"ref": "R1", "pin": "2"},

]

}

],

"layout_strategies": { // Instrucciones globales para el Middleware

"collision_resolution": "shift_right",

"default_track_width": 0.25

}

}

```



Principios de diseño:



· Campo part_def: identifica unívocamente la definición SKiDL que el Middleware importará. Así se evita que el LLM invente nombres de librería. Un módulo validador contrasta cada part_def contra una lista blanca pre-cargada.

· Array pins por componente: declara explícitamente los nombres de pines válidos para ese part. El Middleware puede entonces, durante la creación de redes, verificar que cada pin en connections pertenece a ese conjunto, ofreciendo un mensaje de error preciso si no es así.

· Estrategia de colocación: en lugar de forzar coordenadas absolutas para todos los componentes, se admite strategy (absolute, grid, radial, chained). Los parámetros asociados (grid_params, radial_params) son interpretados por el motor de posicionamiento, que calcula las coordenadas finales. Esto evita que el LLM genere matemáticas de posición y reduce drásticamente las colisiones.

· Pistas opcionales: el JSON puede definir trazas sencillas mediante una polilínea. Si no se incluyen, el Middleware invocará al enrutador automático Freerouting mediante una llamada externa.

· Unidades explícitas y origen de coordenadas: todo en mm, con un grid_origin que permite trasladar masivamente el diseño sin tocar cada componente.



Con esta estructura, el Middleware puede implementar un validador en tres fases:



1. Integridad del esquema (JSON Schema)

2. Consistencia de referencias (todos los ref existen y los pin pertenecen al componente)

3. Reglas de diseño tempranas (no hay dos componentes con la misma referencia, no hay pines no definidos en nets, etc.)

3. Algoritmos: posicionamiento paramétrico sin depender de coordenadas del LLM



Se proponen tres estrategias de distribución para que el Middleware calcule las posiciones a partir de parámetros de alto nivel. Esto evita que el LLM deba calcular coordenadas finas (fuente frecuente de errores) y permite un control determinista del layout.



a) Distribución radial (útil para LEDs, indicadores, conectores circulares)



Parámetros de entrada (por componente o por grupo):



· center_x, center_y (mm)

· radius (mm)

· start_angle (grados, 0 = este, antihorario)

· count (número de elementos en el arco)

· sweep_angle (grados, total del arco; si es 360 se distribuyen en todo el círculo)



Pseudocódigo:



```

function radial_positions(center, radius, start_angle, sweep_angle, count):

if count == 1:

delta = 0

else:

delta = sweep_angle / (count - 1)

positions = []

for i in 0..count-1:

angle = start_angle + i * delta

rad = deg2rad(angle)

x = center.x + radius * cos(rad)

y = center.y + radius * sin(rad)

rotation = angle # el componente mira hacia afuera (o ajustar según tipo)

positions.append( (x, y, rotation) )

return positions

```



Integración: el JSON especifica strategy: "radial" y los parámetros en un bloque común a varios componentes (por ejemplo, un array group). El Middleware asigna a cada componente de ese grupo una de las posiciones calculadas, pudiendo ordenarlas por ref o por secuencia de nets.



b) Distribución en malla (banco de resistencias, capacitores, arrays de LEDs)



Parámetros:



· origin_x, origin_y

· rows, cols

· spacing_x, spacing_y (mm)

· direction: "horizontal" (llenado por filas) o "vertical" (por columnas)



Pseudocódigo:



```

function grid_positions(origin, rows, cols, spacing_x, spacing_y, direction="horizontal"):

positions = []

for r in 0..rows-1:

for c in 0..cols-1:

x = origin.x + c * spacing_x

y = origin.y + r * spacing_y

positions.append( (x, y, 0) )

return positions

```



El Middleware asigna una posición por cada componente del grupo. Si el número de componentes es menor que celdas, se pueden dejar huecos (ajuste spacing). También se puede implementar un ajuste de centrado automático para ocupar todo el espacio disponible.



c) Prevención de colisiones con ajuste por desplazamiento incremental



Cuando el LLM proporciona coordenadas absolutas, existe riesgo de solapamiento. Se propone un algoritmo ligero de “empuje” que se ejecuta en el Middleware (dentro del contexto de pcbnew en la macro de layout) usando los bounding boxes reales de las huellas.



Pasos:



1. Obtener para cada huella su bounding box (footprint.GetBoundingBox() en pcbnew) que devuelve un rectángulo en coordenadas de placa.

2. Insertar componentes uno por uno en el orden dado por el JSON. Para cada componente nuevo, comprobar si su bounding box se solapa con alguno de los ya colocados.

3. Si hay solapamiento, desplazar el componente candidato en dirección +X la cantidad necesaria hasta que no haya solapamiento, manteniendo Y constante. Como fallback, se puede probar desplazamiento +Y.

4. Aplicar el desplazamiento acumulado a la coordenada original.



Pseudocódigo simplificado (dentro de la macro de pcbnew):



```python

def place_with_collision_avoidance(footprint, x_target, y_target, rot, placed_bboxes, step=2.0):

# Obtener bbox del footprint en la posición candidata

bbox_candidate = get_footprint_bbox_at(footprint, x_target, y_target, rot)

attempts = 0

while any(overlap(bbox_candidate, placed) for placed in placed_bboxes):

x_target += step

bbox_candidate = get_footprint_bbox_at(footprint, x_target, y_target, rot)

attempts += 1

if attempts > 100: # límite de seguridad

break

# Colocar el footprint en la posición ajustada

footprint.SetPosition(VECTOR2I_MM(x_target, y_target))

footprint.SetOrientation(EDA_ANGLE(rot, DEGREES))

placed_bboxes.append(bbox_candidate)

```



Este mecanismo garantiza que, incluso si el LLM entrega coordenadas imperfectas, el layout final sea físicamente válido y sin solapamientos graves. Para un control más fino, se puede extender a un desplazamiento en Y o a un pequeño desplazamiento aleatorio amortiguado.



d) Enrutamiento inicial delegado con opción de trazas simples



Para no sobrecargar al LLM, se sugiere:



· Si el JSON proporciona un array tracks con vértices, el Middleware los convierte en pistas de KiCad (pcbnew.PCB_TRACK) asignando la red correspondiente.

· En ausencia de pistas definidas, el Middleware escribe un archivo de sesión para Freerouting y lo invoca como proceso externo. Esto elimina la necesidad de un enrutador propio complejo y garantiza resultados con DRC limpio.

- **Errores de API por cambios de versión.** KiCad 8 usa `VECTOR2I` y `EDA_ANGLE` en la API Python, así que conviene encapsular la conversión geométrica para no depender de suposiciones sobre `wxPoint` o ángulos en grados como flotantes [5].

```python

import pcbnew

import subprocess

import os



def resolve_collision_spiral(board: pcbnew.BOARD, module: pcbnew.FOOTPRINT, step_mm: float = 1.27, max_attempts: int = 50) -> bool:

"""

Resuelve colisiones moviendo el componente en un patrón de espiral cuadrada.

Previene bucles infinitos y aprovecha el espacio en 2D, no solo en un eje.

"""

step_iu = pcbnew.FromMM(step_mm)

original_pos = module.GetPosition()

# Vectores de dirección para la espiral: Derecha, Abajo, Izquierda, Arriba

directions = [(1, 0), (0, 1), (-1, 0), (0, -1)]

dir_idx = 0

segment_length = 1

segment_passed = 0

for attempt in range(max_attempts):

collision = False

module_box = module.GetBoundingBox()

for other_module in board.GetFootprints():

if other_module.GetReference() == module.GetReference():

continue

if other_module.GetBoundingBox().Intersects(module_box):

collision = True

break

if not collision:

return True # Posición segura encontrada

# Calcular siguiente punto en la espiral

dx, dy = directions[dir_idx]

new_pos = pcbnew.VECTOR2I(
```

**Reglas de este Schema:**

* **Mapeo de Pines (valid_pins):** Obliga al LLM a declarar los pines que usará, permitiendo al Middleware validar antes de intentar conectar.

* **Estrategias (layout_strategies):** Reemplaza las coordenadas absolutas. El Middleware interpretará comandos como grid, radial o absolute_cluster.

## 3. Middleware de Validación en 3 Etapas (Python)

El script intérprete ejecutará una validación en cascada antes de compilar el Netlist.

* **Etapa 1: Shadow Interrogator (Verificación Semántica):** El Middleware contrasta el part_def y el footprint contra una lista blanca local (Base de Datos o Diccionario en el entorno). Si el Agente inventa un sufijo o un pin lógico, el proceso se aborta.

* **Etapa 2: Síntesis Lógica (SKiDL):** Construcción del circuito en memoria y ejecución de comprobaciones lógicas (ej. pin no conectado).

* **Etapa 3: Síntesis Física Paramétrica (Macro pcbnew):** Generación del script inyectable en KiCad 8 utilizando VECTOR2I y EDA_ANGLE.

## 4. Algoritmos Físicos y Prevención de Colisiones (pcbnew)

El Middleware autogenerará los cálculos físicos basados en el array layout_strategies.

* **Motor de Empuje (Bounding Box):** Dentro de la macro de KiCad, cada huella será evaluada antes de fijar su posición usando footprint.GetBoundingBox(). Si la caja colisiona con un componente previamente colocado, el algoritmo aplicará un desplazamiento iterativo en el eje +X (en pasos de 1.27mm) hasta encontrar espacio libre.

* **Enrutamiento de Pistas:** Se prohíbe al LLM intentar rutear. El Middleware dejará la placa posicionada con conexiones lógicas (Ratsnest) e invocará automáticamente a **Freerouting** vía *subprocess* para resolver los *Tracks* cumpliendo el *Design Rule Check (DRC)*.

## 5. Bucle de Retroalimentación Tipado (Feedback Loop)

Si la Etapa 1 o 2 del Middleware falla, está estrictamente prohibido devolver un volcado de memoria (Stack Trace) de Python al Agente. El Middleware empaquetará el error en un JSON accionable y lo enviará a la API de Antigraviti.

### 🔬 Escrutinio Técnico Fase 2: Fricciones Detectadas



#### 1. Fricción en el Schema: El weight de `valid_pins` y Multi-Unidades

* **Problema:** Exigir al LLM declarar `valid_pins` en el JSON es innecesario y peligroso. Obliga al modelo a memorizar el archivo `.kicad_sym` exacto. Si el LLM asume que un MOSFET tiene pines `1,2,3` pero la librería usa `G,D,S`, la Etapa 1 fallará. Además, el schema actual no soporta componentes multi-unidad (ej. un 74HC00 con puertas `U1A`, `U1B`).

* **Solución:** Eliminar `valid_pins` del requerimiento del LLM. La validación de pines debe ser *exclusivamente* responsabilidad del Middleware en la Etapa 1 (Shadow Interrogator). Para multi-unidades, añadir un campo opcional `sub_unit` en las conexiones.



#### 2. Fricción en el Algoritmo de Empuje: Destrucción de Estrategias

* **Problema:** El algoritmo de "empuje" (+X en pasos de 1.27mm) entra en conflicto directo con las `layout_strategies`. Si el LLM pide una malla 3x3 de resistencias, y el Bounding Box detecta que la posición de `R5` colisiona con un conector previamente colocado, empujará a `R5` en el eje X. Esto destruye la matriz 3x3, generando un layout basura.

* **Solución:** El motor de colisiones no debe actuar sobre componentes governed por una estrategia paramétrica. Debe actuar *antes*. El Middleware debe calcular el Bounding Box total de la estrategia (ej. el área de la malla 3x3) y verificar si el bloque completo entra en la zona designada. Si colisiona, se desplaza el bloque entero, no el componente individual.



#### 3. Fricción en Freerouting: El Pipeline DSN/SES

* **Problema:** Invocar a Freerouting vía *subprocess* no es tan simple como pasarle un `.kicad_pcb`. Freerouting utiliza el formato Specctra (`.dsn`) y devuelve una sesión de enrutamiento (`.ses`). El Middleware necesita orquestar esta conversión de formatos.

* **Solución:** Documentar explícitamente en el Roadmap el flujo de archivos: `pcbnew` -> Exportar a `.dsn` -> Ejecutar binario de Freerouting -> Generar `.ses` -> Importar `.ses` en `pcbnew` -> Aplicar tracks. Además, se debe incluir un `timeout` en el *subprocess*, ya que Freerouting puede entrar en bucles infinitos en placas densas.



#### 4. Fricción en SKiDL: Jerarquía de Netlists

* **Problema:** SKiDL es excelente, pero si se instancian componentes dinámicamente sin jerarquía, los nombres de las redes (nets) pueden colisionar o generar un netlist plano ilegible para un humano.

* **Solución:** El Middleware debe agrupar los componentes del JSON en bloques jerárquicos de SKiDL (`@SubCircuit`), basándose en metadatos ocultos o agrupaciones lógicas, para que el `.net` resultante sea modular.

3. Middleware de Orquestación (Python)

El pipeline operará en cuatro fases secuenciales:



Fase 1: Shadow Interrogator Dinámico: Al iniciar, el Middleware consulta a la API de KiCad (pcbnew.GetLibraries()) para cargar en RAM los sufijos y footprints disponibles en la máquina local. Valida que el part_def del JSON exista. Si hay alias en el pin_map, los traduce al ID físico requerido por SKiDL.

Fase 2: Síntesis y ERC (SKiDL): Construcción jerárquica del circuito (@SubCircuit) inyectando las unidades (unit: A). Ejecución del chequeo eléctrico. Se exporta el archivo .net.

Fase 3: Síntesis Espacial de Bloques (pcbnew): 1. Se agrupan los componentes según sus layout_strategies.

2. Se calcula el Bounding Box Total del bloque estratégico.

3. Si el bloque colisiona con el contorno de la placa u otro bloque, se aplica el Algoritmo de Espiral Cuadrada al bloque entero (desplazamientos concéntricos en X e Y evaluando el espacio en 360 grados) para no romper la topología interna.

4. Se rotan los componentes empleando pcbnew.EDA_ANGLE().

Fase 4: Enrutamiento Autorizado (Freerouting CLI):

El Middleware exporta el diseño posicionado a Specctra (pcbnew.ExportSpecctraDSN).

Ejecuta Freerouting en modo headless inyectando el design_rules del JSON: java -jar freerouting.jar -de board.dsn -do board.ses -mp 10.

Importa la sesión enrutada (pcbnew.ImportSpecctraSES).

Ejecuta el DRC nativo de KiCad para auditar las pistas generadas.
